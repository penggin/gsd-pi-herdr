# M0.7 — GSD Subagent Execution, Cmux, Loading, Packaging, and Test Audit

## 1. Purpose

Audit the synchronized GSD-Pi baseline before introducing a unified local/cmux/Herdr execution backend. The goal is to identify every behavior currently owned by the bundled subagent extension, every execution call site, current backend asymmetries, packaging constraints, and test gaps.

## 3. Current subagent ownership

The bundled `subagent` extension is the authority for considerably more than process spawning.

It owns:

```text
agent discovery and conflict checks
single / parallel / chain mode validation
status and resume actions
background single dispatch
tracking names and dispatch IDs
project-agent confirmation
model and thinking overrides
fresh and forked child sessions
worktree cwd resolution
optional filesystem isolation
parallel concurrency and retry
JSON event parsing
message, usage, stop-reason, and error accumulation
missing-final-response detection
run-store persistence
worker dashboard registry updates
journal events
isolation delta capture and merge
final tool result rendering
```

A backend refactor must not move these semantics into cmux or Herdr implementations.

## 4. Existing launch contract

`createSubagentLaunchPlan()` already provides the correct semantic input for a backend:

```text
args
child environment
working directory
fresh/fork session metadata
```

The child arguments begin with:

```text
--mode json -p
```

and include session, model, thinking, tools, system-prompt file, and task arguments.

The child environment copies the parent environment and adds:

```text
GSD_SUBAGENT_CHILD=1
GSD_RUNTIME_CONTRACT_ROOT=<validated project root, when applicable>
```

### Coupling found

`launch.ts` imports `shellEscape` from the cmux library solely to implement `buildShellEnvAssignments()`. This makes otherwise generic launch code depend on one backend.

**Refactor requirement:** move shell-command serialization into the cmux backend. The generic launch contract should contain only argv, cwd, environment, and session metadata.

### Herdr implication

Because the environment is copied wholesale, a GSD parent running inside Herdr can pass the main pane's `HERDR_*` identity to a worker. The Herdr runner must strip those values and apply the worker pane's injected identity before spawning the child.

## 5. Current executor implementations

### 5.1 Local executor

`runSingleAgent()`:

1. validates the selected agent and phase conflict;
2. writes the agent system prompt to a protected temporary file;
3. builds the launch plan;
4. spawns `process.execPath` with the GSD entry point, bundled extension arguments, and launch args;
5. uses `shell: false` and piped stdout/stderr;
6. frames stdout by newline and feeds complete records into `processSubagentEventLine()`;
7. streams parent tool updates while the child runs;
8. collects stderr;
9. tracks the `ChildProcess` in `liveSubagentProcesses`;
10. sends `SIGTERM`, then best-effort `SIGKILL` after five seconds on abort;
11. marks missing final responses as errors;
12. cleans prompt artifacts.

This path is the behavioral reference for stream ordering and parent result updates.

### 5.2 Cmux executor

`runSingleAgentInCmuxSplit()` duplicates much of local setup and finalization, then:

1. creates or accepts a cmux surface;
2. builds a shell script;
3. runs the child in `bash -lc`;
4. writes stdout, stderr, and exit code into temporary files;
5. waits for `exit.code` by polling;
6. reads and parses stdout only after process completion;
7. deletes all cmux output evidence before returning.

The command currently uses a pipeline equivalent to:

```bash
child --mode json \
  2> >(tee stderr.log >&2) \
  | tee stdout.jsonl
```

This has four important consequences:

- raw JSONL is copied into the visible terminal;
- structured parent updates are delayed until completion rather than streamed;
- pipeline/process-group cancellation is indirect;
- local and cmux behavior are implemented separately and can drift.

### 5.3 Cmux CLI incompatibility

Current synchronized upstream still calls:

```text
list-surfaces
send-surface
```

and discovers a new split by diffing surface lists. It also sends ETX through `send-surface` for interruption.

The retained downstream branch `fix/cmux-split-cli` changes this behavior, but it is based on the older fork baseline and does not address output streaming, duplicated execution semantics, or all dispatch modes. M0.9 will audit and reimplement valid parts under the unified backend contract.

### 5.4 Unsafe fallback behavior

When cmux surface creation or command delivery fails, the current cmux executor calls the local executor.

That fallback can occur after a visible pane was already created or after launch delivery became ambiguous. It can therefore leave an unused shell pane, create unmonitored work, or risk duplicate execution.

The unified contract must distinguish:

```text
not selected
known pre-launch failure
known launch success
ambiguous launch
known process completion
```

Only a known pre-launch failure may use an explicitly configured fallback.

## 6. Dispatch-mode matrix

| Operation | Current local path | Current cmux path | Isolation behavior | Refactor requirement |
|---|---:|---:|---|---|
| single launch | yes | yes when enabled | wraps executor, captures/merges delta | shared executor |
| parallel launch | yes | yes when enabled | per-task isolation, retry once | shared executor + stable handle per attempt |
| chain | yes | no | current chain path does not create isolation | route through shared executor without changing current isolation semantics |
| background | yes, single only | no | supported for background single | backend must support parent-return lifecycle and durable handle |
| resume | yes | no | resumes stored fork session | route through shared executor |
| status | run-store read only | n/a | n/a | backend-independent |
| retry | local or cmux inside parallel | same surface is intended | isolation recreated per attempt | attempt metadata and stable pane policy |
| fresh context | yes | yes | n/a | preserve launch plan |
| fork context | yes | yes where cmux path is reached | n/a | preserve child session file and directory |

### Limits

```text
maximum submitted parallel tasks: 8
maximum concurrent tasks: 4
parallel automatic retries: 1
background: single mode only
```

These are existing semantics and remain unchanged during the first backend refactor unless a separate decision approves a product change.

## 7. Call-site catalogue

### Resume

The `resume` action selects a stored child session and calls `runSingleAgent()` directly. It currently ignores cmux even when split execution is enabled.

### Background

The background branch supports only single mode and starts an async closure that calls `runSingleAgent()` directly. It returns the run ID immediately. It does not keep an external backend handle or pane identity in the current run-store schema.

### Chain

Each step replaces `{previous}` with the prior final output and calls `runSingleAgent()` directly. A failed step stops the chain. Cmux is not used.

### Parallel

Parallel mode:

- initializes placeholder results;
- creates up to four cmux grid surfaces before worker execution;
- registers an in-memory dashboard worker;
- executes tasks with a concurrency limit of four;
- chooses cmux or local inside `executeOnce()`;
- optionally creates per-task isolation;
- retries a failed task once;
- updates run store and dashboard state;
- merges isolation patches after successful execution.

### Single

Single mode wraps optional isolation around a direct choice between cmux and local execution, then captures and merges isolation deltas.

## 8. Common logic that must be extracted

The following behavior appears in both local and cmux paths or is currently too close to backend code:

```text
result initialization
prompt artifact creation and cleanup
launch-plan creation
bundled extension argv assembly
JSONL framing
processSubagentEventLine invocation
stderr accumulation
onUpdate emission
exit/abort normalization
missing-final-response validation
external runtime metadata attachment
```

Recommended target decomposition:

```text
subagent orchestration
  ├── validates modes and schedules attempts
  ├── wraps isolation
  ├── owns retry/run store/journal/final result
  └── calls executePreparedSubagent()

executePreparedSubagent
  ├── creates shared result collector
  ├── creates launch plan
  ├── selects backend
  ├── accepts stream/lifecycle callbacks
  └── performs one common finalization

backends
  ├── local: direct child process
  ├── cmux: external pane worker transport
  └── herdr: persistent pane worker transport
```

## 9. Result collector requirement

`processSubagentEventLine()` is already backend-neutral. It parses only complete JSONL records and updates messages, usage, model, stop reason, and error data.

M1 should wrap it in a reusable collector object that owns:

```text
partial stdout buffer
complete record ordering
stderr accumulation
current result
parent update emission
finish/abort normalization
missing-final-response validation
```

Local, cmux, and Herdr backends should not each implement this state machine.

## 10. Cancellation and shutdown audit

### Local

- tracked in `liveSubagentProcesses`;
- session shutdown sends `SIGTERM`, waits 500 ms, then `SIGKILL`;
- per-call abort sends `SIGTERM`, then tries `SIGKILL` after five seconds.

### Cmux

- not represented in `liveSubagentProcesses`;
- per-call abort sends terminal Ctrl-C and waits up to five seconds for an exit file;
- no authoritative foreground-process inspection;
- shutdown behavior depends on the active call receiving its abort path;
- temporary artifacts are deleted even when they would help diagnose termination.

### Required abstraction

Introduce an execution-handle registry that can represent local child processes and external pane workers. It must support targeted interrupt, force termination, lifecycle state, external IDs, and shutdown cleanup without pretending every backend exposes a Node `ChildProcess`.

## 11. Isolation ownership

Isolation is correctly positioned mostly outside the actual process transport:

```text
create isolation
→ select isolated cwd/project authority
→ execute child
→ capture delta
→ merge delta
→ cleanup isolation
```

This structure should remain at the orchestration layer. A backend receives the final cwd and environment but does not create or merge worktrees.

Important current behavior to preserve during refactor:

- single, parallel, and background branches can wrap isolation;
- chain currently does not create an isolation environment even when the top-level flag is present;
- parallel retry recreates the task's isolation environment for each `runTask()` attempt;
- merge failure changes an otherwise successful child result to an error.

Any change to chain isolation or retry-isolation reuse is a separate behavior change, not part of backend extraction.

## 12. Persistence and visibility audit

### Durable run store

`SubagentRunStore` writes atomic JSON records under the GSD agent directory and stores child status, output, stderr, model, thinking, usage, session file, cwd, and merge result.

It does not currently store:

```text
backend ID
workspace/tab/pane ID
external launch identity
attempt history
heartbeat
worker artifact directory
ambiguous/orphan state
```

The existing schema can either be extended additively or paired with a dedicated runtime record. M0.8 decides ownership and location.

### Worker registry

`worker-registry.ts` is an in-memory dashboard registry used only by parallel mode. Completed/failed entries are removed after five seconds.

It is not a durability mechanism and should not become the Herdr pane authority. It can be adapted to display richer backend metadata or replaced by a projection from durable execution state.

## 13. Extension-loading and child recursion

The bundled subagent extension exits immediately when `GSD_SUBAGENT_CHILD=1`. This prevents child agents from recursively registering the `subagent` tool.

The loader passes the enabled bundled extension paths into child executions through repeated `--extension` arguments. A future bundled Herdr extension will therefore also be loaded in child JSON processes unless it independently guards its root-session behavior.

Required root reporter conditions remain:

```text
HERDR_ENV == 1
ctx.mode == tui
GSD_SUBAGENT_CHILD != 1
```

Worker-pane state is owned by the worker runner rather than by the root reporter inside the JSON child.

## 14. Build and packaging audit

### Bundled extensions

`src/resources/extensions/**/*.ts` is compiled into `dist/resources` by the resource build. Tests under extension test directories are excluded. Non-TypeScript assets and package manifests are copied.

A future bundled `src/resources/extensions/herdr/` therefore fits the existing build and managed-resource loading model.

### Root npm package

The root package currently ships:

```text
dist
packages/*/dist
packages/*/bin
packages/*/package.json
src/resources
integrations/hermes
selected scripts and metadata
```

It does not yet include `integrations/herdr`. Herdr plugin/docs/assets intended for installed use require a new `files` entry and package-validation assertions.

### Workspace packages

`pnpm-workspace.yaml` includes `packages/*`. The root tarball already includes each package's `dist`, `bin`, `package.json`, and README. A dedicated worker package would fit the distribution layout, but `build:core` enumerates workspace build steps explicitly rather than building every package automatically.

Therefore a new executable workspace package requires:

```text
package directory and tsconfig
bin shim
root build script entry
root dependency coverage where needed
package files/validation updates
installed-tarball resolution test
```

The existing daemon package is a useful precedent for an internal executable shipped through the root tarball.

### `integrations/hermes` precedent

The existing Hermes integration contains plugin metadata, implementation code, scripts, tests, and its own packaging metadata, and the root package explicitly includes it. Herdr can use `integrations/herdr/` for plugin-facing assets and cross-runtime docs/tests while core execution code remains in GSD source/package locations.

## 15. Test audit

### Existing coverage

Subagent tests currently focus on:

```text
agent conflict metadata
launch arguments/environment/session forking
model overrides
run-store behavior
worktree cwd resolution
```

The cmux test covers:

```text
environment/config detection
preference auto-enable behavior
status/progress labels
a locally reproduced grid algorithm
CLI stdin isolation
package auto-discovery opt-out
```

### Critical gaps

There is no focused executor-level suite proving:

```text
local spawn stream/result behavior
cmux command launch and result parity
single/parallel/chain/background/resume backend selection
retry attempt behavior across a backend
abort and shutdown normalization
no-backend regression
ambiguous external launch behavior
raw JSON suppression
external pane metadata persistence
local-vs-external final result parity
```

The current cmux grid tests reproduce the layout algorithm inside a mock object rather than invoke `CmuxClient.createGridLayout()`. The CLI test explicitly expects the obsolete `list-surfaces` command, so it currently locks in the incompatible implementation.

## 16. M1 implementation boundaries derived from the audit

M1 should proceed in the following internal order:

1. Introduce backend-neutral execution types and an execution handle.
2. Extract one result collector/finalizer around `processSubagentEventLine()`.
3. Move direct spawn into `LocalSubagentBackend` without semantic change.
4. Route all one-attempt execution through one helper.
5. Update resume, background, chain, parallel, and single call sites to use it.
6. Preserve isolation and retry at the orchestration layer.
7. Move shell serialization out of `launch.ts`.
8. Port cmux to the contract using current CLI commands.
9. Replace the cmux JSON tee with a filtered worker transport.
10. Add fake backends and result-parity tests before adding Herdr.

Herdr implementation should begin only after the local backend passes parity tests and the cmux port proves the contract supports an external pane transport.

## 17. Decisions carried into M0.8

The audit supports these placement tendencies, to be finalized in M0.8:

- generic backend types, collector, registry/selector, and local backend belong under `src/resources/extensions/subagent/`;
- the cmux backend adapter belongs near the subagent backend layer, while generic cmux sidebar/notification utilities may remain in `src/resources/extensions/cmux/`;
- Herdr main-session reporting, preferences, capability detection, and adapter glue belong in a bundled `src/resources/extensions/herdr/` directory;
- the external worker runner is better represented as an executable workspace package than as a copied extension script, subject to build/package validation;
- Herdr plugin-facing assets, long-form integration docs, and real-Herdr E2E fixtures remain under `integrations/herdr/`;
- run-store schema ownership stays with the subagent extension, while runtime evidence may use a Herdr-specific state root referenced by additive child metadata.
