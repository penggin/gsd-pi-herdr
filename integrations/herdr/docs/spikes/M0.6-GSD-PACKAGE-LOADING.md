# M0.6 — GSD-Pi Package and Resource Loading Investigation

> Migrated from `penggin/gsd-herdr@d13fbe85ad584dd7505a5420d668c780ac137726`.

## Question

Could a standalone integration modify only installed `src/resources` files and have released GSD-Pi load the modified bundled subagent extension?

## Baseline inspected

```text
repository: open-gsd/gsd-pi
tag:        v1.16.2
commit:     dda097fc89ce10b67e78faa0b947c22bb9ec96a2
```

## Findings

### Production prefers compiled resources

`resolveBundledResourcesDirFromPackageRoot()` selects `dist/resources` whenever it contains complete `agents` and `extensions` trees. It falls back to `src/resources` only when the compiled tree is incomplete.

### Release builds compile resource TypeScript

The resource build compiles `src/resources/extensions/**/*.ts` and shared TypeScript into `dist/resources`, copies non-TypeScript assets, and writes `.managed-resources-content-hash`.

### Startup synchronizes bundled resources

`initResources()` copies bundled extensions and other managed resources into the GSD agent directory before normal extension loading. Print/subagent mode also performs this synchronization.

### Fingerprinting matters

When package version and managed content fingerprint match, the synchronizer may skip copying. Modifying compiled resources without regenerating the fingerprint can leave the old managed extension active.

### Direct managed-directory edits are not durable

Editing `~/.gsd/agent/extensions/subagent` may appear to work temporarily but can be overwritten by the next managed resource refresh.

## Original conclusion

A safe standalone resource overlay would require:

1. exact upstream version verification;
2. source patching;
3. compilation into `dist/resources`;
4. fingerprint regeneration;
5. controlled managed-resource resynchronization;
6. verification of installed file digests.

A `src/resources`-only overlay was rejected.

## Consequence after repository consolidation

The primary distribution is now the full managed source fork `penggin/gsd-pi-herdr`. Therefore the normal path is:

```text
source change
→ normal GSD build:core / resource compilation
→ downstream package/release validation
→ downstream installation
```

We no longer need a production resource-overlay mechanism for the primary build. The investigation remains useful because:

- package validation must include Herdr resource and worker assets;
- source changes under `src/resources` still require the normal resource build;
- stale fingerprints can still affect development or partial-build workflows;
- tests must run against the same built/managed copies that production loads.

## Follow-up requirements

- Add Herdr extension/runner/plugin assets to package `files` and validation only after M0.8 chooses their final locations.
- Ensure relevant tests exercise built resources or explicitly document source-mode behavior.
- Never claim a raw `src/resources` edit represents a production installation.
