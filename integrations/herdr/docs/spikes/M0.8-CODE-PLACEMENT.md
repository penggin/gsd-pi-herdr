# M0.8 — Final Code and Package Placement

## 1. Decision summary

The Herdr runtime will be implemented as a first-class downstream GSD feature using three in-tree layers:

```text
GSD bundled resource extensions
  ├── subagent execution backends
  └── root Herdr session integration

@gsd/herdr-runtime workspace package
  ├── typed socket client
  ├── capability detection
  ├── shared schemas/artifact helpers
  └── worker-runner executable

integrations/herdr
  ├── Herdr plugin assets
  ├── cross-runtime E2E fixtures
  └── planning, operations, and compatibility documentation
```

No production resource overlay or separate `gsd-herdr` package is required for the primary downstream distribution.

## 3. Why `@gsd/herdr-runtime` is one workspace package

The typed Herdr client, capability parser, artifact schemas, and worker executable are needed by more than one runtime context:

```text
subagent Herdr backend
root Herdr extension
worker runner
operations/plugin scripts
contract and E2E tests
```

Keeping them inside one bundled extension would make the executable path and reuse awkward. Splitting them into several packages would add build/release overhead before there is evidence that independent versioning is useful.

One internal package provides:

- a single module identity and API boundary;
- a stable executable location;
- normal TypeScript compilation and unit tests;
- reuse without cross-extension singleton assumptions;
- inclusion through the root package's existing `packages/*/dist`, `packages/*/bin`, and `packages/*/package.json` patterns;
- a future extraction point if the runtime becomes independently useful.

Proposed package metadata:

```json
{
  "name": "@gsd/herdr-runtime",
  "private": true,
  "type": "module",
  "main": "./dist/index.js",
  "types": "./dist/index.d.ts",
  "bin": {
    "gsd-herdr-worker": "./bin/gsd-herdr-worker.js"
  },
  "gsd": {
    "linkable": true,
    "scope": "@gsd",
    "name": "herdr-runtime"
  }
}
```

The package remains private in the first downstream release and ships as part of the root GSD tarball.

## 4. Subagent execution layer

### Generic contract location

Backend-neutral types, collector, selector, and one-attempt executor belong under:

```text
src/resources/extensions/subagent/execution/
```

Reasons:

- they are internal to the existing bundled subagent feature;
- they must access the current result parser and tool update behavior;
- keeping them close makes upstream merges and semantic review easier;
- no new cross-package public API is needed for GSD orchestration internals.

### Backend implementations

Local, cmux, and Herdr backends also live under the execution layer. This makes backend selection explicit and ensures all implementations obey one contract.

The Herdr backend may import public infrastructure from `@gsd/herdr-runtime`, but `@gsd/herdr-runtime` must not import the bundled subagent extension.

Dependency direction:

```text
subagent orchestration
  → execution contract/collector
    → local backend
    → cmux backend
    → Herdr backend
      → @gsd/herdr-runtime
```

### Cmux library boundary

Generic cmux environment detection, sidebar status, notification, and low-level CLI operations may remain in:

```text
src/resources/extensions/cmux/
```

Subagent-specific process transport moves into `subagent/execution/backends/cmux.ts`. The backend consumes a low-level `CmuxClient`; the client does not parse GSD JSON events or decide fallback.

### Launch module cleanup

`launch.ts` remains backend-neutral. Shell escaping and environment-assignment string generation move to the cmux backend or a backend-local utility.

## 5. Bundled Herdr extension

Root-session state and user-facing integration diagnostics belong in:

```text
src/resources/extensions/herdr/
```

It is a normal bundled extension because it participates in GSD lifecycle events and user configuration.

Responsibilities:

```text
root TUI Herdr authority
milestone/slice/task state projection
Herdr preference resolution
status and doctor commands
startup capability diagnostics
shutdown/reload release
```

Non-responsibilities:

```text
subagent orchestration
JSON result parsing
worker child spawning
worktree isolation
retry policy
pane-pool business logic inside the root reporter
```

The extension and Herdr backend both use `@gsd/herdr-runtime` instead of importing one another through extension-loader-specific state.

## 6. Worker runner

The worker runner belongs in `packages/herdr-runtime`, not in a raw bundled extension directory.

Reasons:

- it is a standalone executable process;
- it needs focused process, signal, stream, artifact, and security tests;
- it should run from an immutable built package path rather than a managed extension copy;
- the backend can resolve it from `GSD_PKG_ROOT` or the linked workspace package;
- package validation can assert the bin and built files exist after npm installation.

The runner receives a protected launch artifact path, not raw task/prompt values interpolated into a shell command.

## 7. Herdr plugin and integration assets

The operations plugin, user documentation, compatibility evidence, and real-Herdr tests remain under:

```text
integrations/herdr/
```

Only install/runtime assets need to ship in the npm package. Planning documents can remain in git and may optionally ship for support visibility.

Recommended package inclusion:

```text
integrations/herdr/plugin
integrations/herdr/README.md
integrations/herdr/docs/OPERATIONS.md
integrations/herdr/docs/SECURITY.md
```

The exact shipping list is finalized during M6 and guarded by `validate-pack`.

## 8. Configuration placement

Herdr backend selection and behavior are GSD runtime preferences, so they belong in the existing GSD preference schema rather than a second user config file.

Expected touched files:

```text
src/resources/extensions/gsd/preferences-types.ts
src/resources/extensions/gsd/preferences-validation.ts
src/resources/extensions/gsd/preferences.ts or serializer modules
relevant setup/config command code
```

Proposed top-level keys remain conceptually:

```yaml
subagents:
  runtime: herdr
  monitoring_required: true

herdr:
  enabled: true
  layout: ...
  display: ...
  retention: ...
  recovery: ...
```

M1/M2 may refine naming to match existing GSD conventions. Existing projects with no new keys must preserve current local/cmux behavior.

## 9. Run-store and runtime-evidence placement

### GSD run store

`src/resources/extensions/subagent/run-store.ts` remains the user-facing durable status/result authority.

Additive child metadata may include:

```text
backend ID
workspace/tab/pane ID
external execution ID
attempt IDs
runtime artifact directory
last known external state
```

### Herdr runtime artifacts

Detailed launch, heartbeat, stdout, stderr, state, and exit evidence is owned by `@gsd/herdr-runtime` under an integration-specific protected state root.

The run store references those artifacts but does not duplicate all raw data.

This preserves the distinction:

```text
GSD run store = semantic status/result projection
Herdr runtime store = process and transport evidence
```

## 10. Test placement

| Test type | Location |
|---|---|
| backend contract, selection, local/cmux parity | `src/resources/extensions/subagent/tests/` |
| root reporter and Herdr preferences | `src/resources/extensions/herdr/tests/` |
| socket client, schemas, worker process | `packages/herdr-runtime/src/**/*.test.ts` |
| plugin contract and fake Herdr integration | `integrations/herdr/tests/contract/` |
| real Herdr detach/recovery E2E | `integrations/herdr/tests/e2e/` |

Root test scripts must be updated so these locations are compiled and executed explicitly. Tests should not be hidden in a path that the current `test:unit:compiled` glob ignores.

## 11. Build changes required

Creating `packages/herdr-runtime` requires:

1. package manifest and TypeScript configuration;
2. a `build:herdr-runtime` root script;
3. inclusion in `build:core` before resource compilation and package validation;
4. workspace dependency/link metadata;
5. root dependency coverage for any external runtime packages;
6. bin-shim validation;
7. installed-tarball import/execute smoke tests;
8. version-sync handling if the package version follows root releases.

Creating `src/resources/extensions/herdr/` requires no new resource compiler pattern, but it requires:

```text
extension manifest
preference types/validation
unit-test inclusion
managed-resource/package validation
```

Shipping Herdr plugin assets requires a root `files` entry and `validate-pack` assertions.

## 12. Herdr core position

No files are allocated for a Herdr source patch. A future limitation would be documented first and, only if necessary, managed under a new explicit downstream mechanism.

The initial implementation consumes official Herdr releases through the public API validated in M0.6.

## 13. Implementation order implied by placement

```text
1. scaffold @gsd/herdr-runtime with schemas/client tests
2. create subagent execution contract and collector
3. port local backend and prove parity
4. port/fix cmux backend and filtered transport
5. add bundled Herdr extension and diagnostics
6. add Herdr backend and worker runner
7. add plugin assets and cross-runtime E2E
8. update package/release validation
```

The first implementation milestone still begins with the execution contract, not Herdr pane creation.

## 14. M0.8 outcome

```text
generic execution core: src/resources/extensions/subagent/execution
local/cmux/Herdr backend adapters: subagent execution layer
root Herdr lifecycle integration: src/resources/extensions/herdr
shared Herdr client/protocol/worker: packages/herdr-runtime
Herdr plugin/docs/E2E: integrations/herdr
user configuration: existing GSD preferences
semantic run status: existing subagent run store, extended additively
raw process evidence: Herdr runtime state root
Herdr source patch: none
```

M0.8 is complete. M0.9 will determine how to preserve the existing cmux branch's valid behavior inside the new execution layer.
