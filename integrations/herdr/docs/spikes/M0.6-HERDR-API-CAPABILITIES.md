# M0.6 — Herdr API Capability Validation

## 1. Question

Can the first GSD-Pi Herdr runtime be implemented against public Herdr plugin, CLI, and socket APIs without maintaining a Herdr core fork?

This spike also establishes which API capabilities are mandatory, which are preferred, and which CLI conveniences must not be mistaken for raw socket methods.

## 2. Sources inspected

### Stable baseline

The comparison was performed against the checked-in JSON schemas and current socket API documentation. No assumption was made from the Herdr version number alone.

## 3. Result

**Schema-level feasibility is confirmed.** Herdr `v0.8.2` protocol 20 already exposes the pane, layout, state-reporting, process-inspection, event, snapshot, and plugin methods needed for the initial GSD worker runtime.

No mandatory first-release behavior currently requires a Herdr core patch.

A real `v0.8.2` binary/socket smoke test is still required before implementation is declared runtime-verified. This spike proves the public contract exists; it does not prove every operation behaves correctly under load, detach/reattach, or failure injection.

## 5. Important request and response shapes

### 5.1 `session.snapshot`

Request parameters are empty. The response contains:

```text
version
protocol
focused workspace/tab/pane IDs
workspaces
tabs
panes
layouts
agents
```

This is sufficient to bootstrap reconciliation after extension reload, GSD restart, Herdr client reattachment, or Herdr server recovery. Snapshot data is evidence about Herdr state; durable GSD worker artifacts remain the authority for child completion.

### 5.2 `tab.create`

The request may specify:

```text
workspace_id
cwd
env
label
focus
```

The response includes the created tab and its root pane. This supports a dedicated `GSD Workers` tab without stealing focus from the main GSD pane.

### 5.3 `layout.apply`

`layout.apply` accepts a declarative binary-split tree. Pane nodes may contain:

```text
pane_id
label
cwd
env
command: string[]
```

Split nodes contain:

```text
direction: right | down
ratio
first
second
```

The response returns the authoritative applied layout. This allows a one-, two-, or four-pane worker grid to be created with argv-based commands and pane-specific environment in one operation.

**Decision:** prefer `layout.apply` for deterministic worker-tab creation and restoration. Use `pane.split` for incremental repair, adaptive growth, or implementations where applying a new layout would replace an existing live tab.

### 5.4 `pane.split`

The request requires `direction` and may specify:

```text
workspace_id
target_pane_id
cwd
env
focus
ratio
right_click
```

It creates a terminal pane but does not itself carry a command array. A command can subsequently be delivered by a safe public input method, or the integration can use `layout.apply` when command-at-creation is needed.

### 5.5 `pane.process_info`

The response can include:

```text
shell_pid
foreground_process_group_id
foreground_processes[]
tty
```

This is valuable for pane-loss reconciliation, PID-reuse protection, targeted cancellation verification, and orphan diagnosis. The integration must still combine it with its own launch identity and artifacts rather than trusting a PID alone.

### 5.6 `pane.send_keys` and `pane.send_input`

`pane.send_keys` requires a pane ID and an array of key-combo strings. It is the preferred public path for targeted `ctrl+c` delivery.

`pane.send_input` can combine text and keys and is optional for the first implementation. Signal success must be confirmed through process/final evidence, not assumed from a successful input request.

### 5.7 State and authority reporting

`pane.report_agent` requires:

```text
pane_id
source
agent
state: idle | working | blocked | unknown
```

It also supports a bounded message, sequence number, and session ID/path.

`pane.report_agent_session` associates a pane authority with a session ID or path.

`pane.report_metadata` supports title, display agent, state labels, bounded tokens, sequence number, and optional TTL.

`pane.release_agent` requires the same pane/source/agent authority tuple and optionally a sequence number.

These methods support separate main-pane and worker-pane authority domains. They also make monotonic sequence numbers and explicit release part of the integration contract.

### 5.8 Pane reads and events

`pane.read` can read `visible`, `recent`, `recent_unwrapped`, or `detection` output in text or ANSI form.

The event API includes pane creation, closure, updates, focus, movement, output changes, process exit, agent detection/status changes, and layout updates. Event subscriptions reduce polling, while snapshots remain necessary for initial state and reconnect reconciliation.

## 6. Raw socket methods versus CLI helpers

Herdr documentation exposes convenient commands such as:

```bash
herdr pane run ...
```

However, **`pane.run` is not a raw socket method in the validated schemas.** It is a CLI convenience that composes lower-level behavior.

The GSD integration must therefore not declare `pane.run` as a mandatory socket capability. The implementation should use one of these public, schema-backed paths:

1. preferred: `layout.apply` with a pane `command` argv array;
2. incremental fallback: create/split a pane, then deliver a fixed runner command through a validated input operation;
3. use a CLI wrapper only behind an explicit CLI adapter with its own versioned tests.

Likewise, `agent.start` is designed for recognized interactive coding-agent manifests. The GSD child is a headless JSON worker wrapped by `gsd-herdr-worker`, so it should not depend on Herdr treating that child as a native interactive agent.

## 7. Protocol 20 to 21 compatibility position

Protocol 21 adds or expands useful capabilities, including richer plugin and metadata surfaces and additional terminal functionality. None of those additions are required to prove the initial worker backend feasible.

The client must:

- parse the installed schema or probe methods rather than compare one exact protocol number;
- require a named capability set such as `gsd-herdr-runtime-v1`;
- tolerate unknown response fields;
- reject missing required fields or incompatible request shapes;
- record the observed Herdr version, protocol, and capability set in diagnostics;
- run contract tests against both the pinned stable schema and current master.

`gsd-herdr-runtime-v1`:

Optional capabilities are enabled independently and must not cause an otherwise compatible stable Herdr installation to be rejected.

## 9. Architecture consequences

1. Keep Herdr external; no core fork is justified by M0.6.
2. Build a typed Herdr client around schema-backed socket methods.
3. Prefer `layout.apply` for initial worker-grid creation and command-at-creation.
4. Keep `pane.split` for incremental layout repair and compatibility.
5. Treat `pane.run` as a CLI adapter feature, not a socket contract.
6. Use `session.snapshot` plus events and durable local artifacts for reconciliation.
7. Use `pane.process_info` only as corroborating process evidence.
8. Separate root GSD authority from each worker authority and release both explicitly.
9. Support `v0.8.2` protocol 20 as the first stable baseline; test current protocol 21 as canary.

## 10. Remaining verification

Before M2/M3 can claim runtime support, execute against real Herdr binaries:

- export and parse `herdr api schema --json` from `v0.8.2`;
- create a test workspace/tab and apply a two-pane command layout;
- verify pane environment injection and returned IDs;
- report, update, and release agent/session/metadata authority;
- read pane output and inspect process information;
- deliver `ctrl+c` and confirm the intended foreground process group exits;
- detach and reattach while the worker continues;
- restart/reconnect and compare `session.snapshot` with durable records;
- validate plugin link/action/pane behavior.

These tests belong to the implementation and E2E phases. Their absence is a known evidence gap, not a blocker for the schema-level feasibility decision.

## 11. Decision

M0.6 is complete at the public-contract level:

```text
Herdr core fork required for MVP: no
Pinned stable protocol: 20 (Herdr v0.8.2)
Current canary protocol: 21
Preferred layout/launch method: layout.apply with command argv
Incremental fallback: pane.split + validated command delivery
Required compatibility test: capability set, not exact protocol equality
Real binary/socket E2E: still required
```
