# M0.10 Final Feasibility Summary

> Status: complete  
> Date: 2026-08-29  
> Downstream GSD base: `4b26a642c0121ae6161abbb6f2dc6937c78874dd`  
> Initial Herdr target: `v0.8.2` (`9eb521456ac0d19d3ab3d9d7cea3cca10baa8a4c`, protocol 20)

## Executive conclusion

The Herdr integration is feasible as a first-class feature of the managed `penggin/gsd-pi-herdr` downstream fork without maintaining a Herdr core fork.

The original external-overlay/minimal-patch architecture is no longer appropriate. The fork should instead refactor GSD's existing subagent execution into one common semantic runner with runtime backends:

```text
Subagent orchestration / result semantics
        │
        └── common one-child runner
            └── runtime backend
                ├── LocalBackend
                ├── CmuxBackend
                └── HerdrBackend
```

This simultaneously enables Herdr and fixes structural duplication already present between local and cmux execution.

## Evidence completed in M0

### Repository/downstream strategy

- `penggin/gsd-pi-herdr` was selected as the long-term downstream distribution.
- The fork had no unique commits on `main` before integration work.
- `main` was fast-forwarded from `c2e61def5d6d3d8c516d115a53654b229f658915` to current upstream `4b26a642c0121ae6161abbb6f2dc6937c78874dd`.
- `upstream-main` represents the pristine upstream synchronization line.
- The historical cmux fix remains isolated on `fix/cmux-split-cli` for deliberate incorporation during backend extraction.

### Historical GSD packaging spike

- Released GSD uses built `dist/resources` when complete, then synchronizes managed extension copies.
- A `src/resources`-only overlay against a published package was not a robust production mechanism.
- This concern is resolved architecturally by building/releasing the managed downstream fork rather than patching an installed upstream package.

### Herdr capability spike

Herdr v0.8.2 provides the public capabilities needed for the first stable design:

- tabs and panes;
- split/layout operations;
- pane process/output/input inspection;
- atomic CLI `pane run` command submission;
- semantic state/session/metadata reporting and release;
- session snapshot;
- events;
- plugin actions/startup hooks/panes.

No required M1–M4 behavior currently requires a Herdr core patch.

### Current GSD subagent execution spike

The current code has two duplicated single-child execution pipelines:

- local direct spawn;
- cmux external shell/pane execution.

Runtime selection is inconsistent by mode:

```text
resume       -> local only
background   -> local only
chain        -> local only
parallel     -> local or cmux
single       -> local or cmux
```

The cmux path also differs in phase guard, streaming updates, abort classification, output durability, fallback, and shutdown ownership. Therefore Herdr must not be added as a third duplicated helper.

## Architecture decisions finalized

1. **Managed downstream fork** — this repository owns downstream architecture and may contain deliberate custom fixes/refactors.
2. **Official Herdr** — consume public APIs/CLI; fork only after a proven missing capability.
3. **One semantic child runner** — result parsing and GSD semantics are shared above Local/Cmux/Herdr runtimes.
4. **JSON-mode children stay** — structured output remains the parent contract.
5. **Internal worker runner** — Herdr panes run a downstream internal GSD worker entrypoint, not a raw JSON `tee` shell pipeline.
6. **Root and worker authority are separate** — headless children cannot overwrite root-pane lifecycle/session state.
7. **Required observability is correctness** — no silent local fallback after Herdr execution is selected/possibly launched.
8. **Capability-driven Herdr support** — version is recorded, but actual required methods/CLI behaviors are validated.
9. **Strong downstream test matrix** — semantic parity protects against AI-assisted but semantically wrong upstream conflict resolution.

## Implementation phases and revised estimates

Estimates are engineering effort ranges, not calendar promises.

### M1 — Root GSD ↔ Herdr integration: 1–3 focused development days

Deliver:

- Herdr preferences/detection;
- reusable client/capability helpers;
- root session semantic state/session/metadata reporting;
- root/child authority guards;
- diagnostics and tests.

This work is largely independent from subagent backend refactoring and gives an early real Herdr integration checkpoint.

### M2 — Subagent backend refactor: 3–6 focused development days

Highest-risk structural milestone.

Deliver in safe stages:

1. runtime backend interfaces;
2. LocalBackend extraction;
3. common semantic runner and local parity;
4. migrate resume/background/chain/parallel/single to the common runner;
5. extract CmuxBackend;
6. reapply/revalidate current cmux CLI fix;
7. eliminate duplicated cmux result/parser pipeline;
8. add mode/backend/parity/shutdown tests.

Do not start Herdr worker execution until local parity is solid.

### M3 — Internal Herdr worker runner: 2–4 focused development days

Deliver:

- secure artifact schemas/paths;
- internal worker CLI entrypoint;
- JSON child spawn/capture;
- filtered renderer;
- Herdr worker state reporting;
- environment authority rewrite;
- heartbeat/final evidence;
- signal escalation and security tests.

### M4 — HerdrBackend + persistent worker pool: 3–6 focused development days

Deliver:

- worker tab/pool management;
- bounded four-slot reuse;
- CLI `pane run` launch;
- JSONL relay into common parser;
- pane cancellation and launch reconciliation;
- single/parallel/chain result parity;
- required-backend failure behavior.

At M4 exit the feature is expected to be practically usable for monitored subagents.

### M5–M6 — Operations + durability: 4–8 focused development days

Deliver dashboard/focus/cleanup plugin or equivalent UX, plus crash/orphan/restart reconciliation and detach/reattach E2E.

### M7 — Downstream maintenance/release automation: 2–4 focused development days

Deliver upstream watch, compatibility reports, downstream release metadata, canary/rollback documentation/automation.

### Rough total

A robust first stable implementation is approximately **15–31 focused engineering days** under the current scope. AI assistance may reduce elapsed human effort significantly, but M2/M4/M6 are test-heavy because correctness depends on process/runtime semantics, not just code volume.

## Exact first implementation sequence

### M1 entry checklist

1. Extend GSD preference types/validation with the minimal Herdr block required for root integration only.
2. Add `src/resources/extensions/herdr/` as a bundled integration/library surface with no subagent execution yet.
3. Implement `detectHerdrEnvironment()` and capability model.
4. Implement a bounded Herdr request/CLI client layer.
5. Add root reporter:
   - TUI only;
   - ignore `GSD_SUBAGENT_CHILD=1`;
   - report session ID/path;
   - working/blocked/idle;
   - milestone/slice/task metadata;
   - release on shutdown.
6. Add focused tests with a fake Herdr server/client adapter.
7. Validate against real Herdr v0.8.2 in an isolated session.

### M2 entry checklist after M1

1. Add tests around the existing local `runSingleAgent()` result semantics before moving code.
2. Define backend execution evidence/callback types.
3. Extract direct `spawn()` mechanics to LocalBackend without changing any caller selection.
4. Make the common runner consume LocalBackend and prove parity.
5. Only then migrate all call sites and extract cmux.

## Known pre-existing issues deliberately separated from pure refactor

M0 identified behavior that may deserve downstream fixes but should not be mixed invisibly into the first parity extraction:

- chain mode currently ignores the tool-level `isolated` flag;
- cmux currently bypasses the local phase-conflict guard;
- cmux abort classification differs from local;
- cmux raw JSON is `tee`d to the pane;
- cmux current main still uses stale CLI commands fixed on the historical branch;
- cmux session-shutdown ownership is weaker than direct local child ownership;
- an eight-task parallel batch can create more than the initially pre-created four cmux panes instead of reusing a bounded pool.

The last five are closely tied to backend extraction and may need correction as part of M2. Chain-isolation behavior should be a separate explicit change after the parity baseline.
