## Important distinction: `pane run` is CLI-only in v0.8.2

The raw method table contains:

```text
pane.send_text
pane.send_keys
pane.send_input
```

but does **not** list a raw socket method named `pane.run`.

The CLI does expose:

```bash
herdr pane run <pane_id> <command>
```

and documents it as bracketed-paste-aware and atomically submitting the command plus Enter. It is explicitly preferable to a separate `send-text` + `send-keys enter` sequence for shell commands.

### Implementation consequence

For the first HerdrBackend implementation:

- use a raw socket/API client for state, metadata, discovery, snapshot, and subscriptions where useful;
- use the Herdr CLI `pane run` for launching the internal GSD worker command in an existing pooled shell pane;
- do not invent a raw JSON request `method: "pane.run"`.

A later Herdr release may provide a direct process-launch method; capability detection can switch implementation then.

## Tab and pane creation behavior

v0.8.2 CLI supports:

```bash
herdr tab create \
  [--workspace <workspace_id>] \
  [--cwd PATH] \
  [--label TEXT] \
  [--env KEY=VALUE] \
  [--focus|--no-focus]
```

The response exposes the created tab and root pane IDs.

Pane splitting supports:

```bash
herdr pane split [<pane>|--pane ID|--current] \
  --direction right|down \
  [--ratio FLOAT] \
  [--cwd PATH] \
  [--env KEY=VALUE] \
  [--focus|--no-focus]
```

Important: the documented split directions are `right` and `down`, not cmux's broader directional surface. The Herdr pool layout should be built from these two directions or `layout.apply` rather than assuming left/up split creation.

Workspace/tab/pane creation defaults to preserving focus unless explicitly focused, which aligns with the desired `preserve_main_focus` policy.

## Managed environment behavior

Herdr documents that process-launching methods inject authoritative runtime variables including:

```text
HERDR_SOCKET_PATH
HERDR_ENV=1
HERDR_WORKSPACE_ID
HERDR_TAB_ID
HERDR_PANE_ID
```

and that Herdr-managed variables win when caller-provided env conflicts.

This is important for the worker design: the internal runner executes inside the real worker pane and can use its own injected pane identity. The runner must strip the root pane's copied Herdr IDs from the GSD launch environment before spawning the real JSON-mode child.

## Semantic agent state reporting

Example raw report:

```json
{
  "method": "pane.report_agent",
  "params": {
    "pane_id": "w1:p1",
    "source": "custom:gsd",
    "agent": "gsd",
    "state": "working",
    "message": "M04/S02"
  }
}
```

The CLI syntax accepts reported states:

```text
idle | working | blocked | unknown
```

Herdr exposes `done` as an effective/read-side state (idle and not yet seen), not as the lifecycle value we should depend on reporting through the initial CLI surface.

### Worker mapping

```text
starting/working -> working
retrying         -> working + retry message/metadata
blocked          -> blocked
completed        -> idle + completed metadata
orphaned         -> unknown (or blocked if operator attention is required)
```

The exact failed/aborted retention presentation can be finalized during M4.

## Session identity

`pane.report_agent_session` allows session identity to be updated independently from lifecycle state and accepts native session ID/path fields. This is suitable for root GSD session reporting and, where useful, forked child session references.

## Metadata

`pane.report_metadata` is explicitly display-only and does not replace semantic lifecycle authority. It supports:

- title;
- display-agent;
- labels for effective states;
- bounded named tokens;
- TTL;
- source sequence ordering.

This fits worker presentation such as model, tracking name, recent activity, completion markers, and retry counts without abusing lifecycle state.

Text is normalized and bounded by Herdr; the GSD side should still redact/cap before reporting.

## Sequence ordering

Herdr supports `seq`. For a given source, reports at or below the last accepted sequence can be accepted by the API but ignored by state. The GSD integration should use monotonically increasing source-local sequence values where concurrent/async updates could reorder.

## Process inspection and cancellation

`pane.process_info` reports shell/foreground process information where available. `pane.send_keys` accepts `ctrl+c` syntax.

This provides two useful cancellation/reconciliation signals:

1. GSD can send an interrupt to the exact Herdr worker pane;
2. the backend can inspect whether the intended runner/child is still foreground/alive before declaring an ambiguous launch lost.

The internal runner still owns child process-group escalation after it receives SIGINT.

## Snapshot and events

`session.snapshot` returns workspaces, tabs, panes, layouts, focus IDs, and agent records. It is appropriate for cold bootstrap/reconciliation.

`events.subscribe` supports pane lifecycle events including creation, close, exit, movement, update, agent detection/status changes, and output matches. First implementation may use bounded polling/artifacts where simpler, but event subscriptions are available for later event-driven pane-loss detection.

## Plugin capability

Herdr v0.8.2 plugin v1 supports:

- startup hooks;
- actions;
- event hooks;
- managed pane entrypoints;
- link handlers;
- injected plugin config/state paths and context;
- plugin lifecycle APIs.

Therefore an optional GSD operations plugin can provide dashboard/focus/cleanup/startup-reconciliation functions without modifying Herdr core.

Core subagent execution should remain GSD-side so the plugin is not a correctness dependency unless a future decision changes that.

## Decision

**M0.7 passes.** Herdr v0.8.2 is sufficient for the planned first-class GSD integration using public API/CLI surfaces.

Initial integration contract:

- official Herdr binary, no core fork;
- Herdr raw socket/API for semantic state, metadata, discovery, snapshots, optional subscriptions;
- Herdr CLI `pane run` for atomic worker command submission;
- `tab.create` + `pane.split` or `layout.apply` for bounded worker pool topology;
- `pane.send_keys ctrl+c` + internal runner process-group handling for cancellation.

## Follow-up

The next feasibility task is no longer package-overlay evaluation. Because the integration is now inside the managed GSD fork, the next task is to inspect the **current post-upstream-sync subagent implementation** and map every execution branch into the proposed Local/Cmux/Herdr backend abstraction without losing single/parallel/chain/background/retry/fork/isolation behavior.
