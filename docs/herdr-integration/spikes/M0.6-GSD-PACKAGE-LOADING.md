# M0.6 Historical Spike — GSD-Pi Package/Resource Loading

> Status: completed in the original `penggin/gsd-herdr` planning repository on 2026-08-29. Preserved after moving the integration into the managed downstream fork.

## Question

Could a separately installed integration safely modify a released GSD-Pi package by overlaying only `src/resources/extensions/subagent/...`, avoiding a full downstream build?

## Baseline inspected

- upstream release: GSD-Pi `v1.16.2`;
- release tag commit: `dda097fc89ce10b67e78faa0b947c22bb9ec96a2`;
- package ships both `dist` and `src/resources`.

## Production resource selection

`src/bundled-resource-path.ts` chooses:

```text
<package>/dist/resources
```

when that tree contains the expected bundled `agents` and `extensions` directories. Only an incomplete/missing built tree falls back to:

```text
<package>/src/resources
```

Therefore a normal published package does not treat a changed `src/resources` tree as the authoritative runtime bundle.

## Build pipeline

The release build compiles resource TypeScript through `tsconfig.resources.json` into `dist/resources`, copies non-TypeScript resources, and writes:

```text
dist/resources/.managed-resources-content-hash
```

The package publication workflow runs the core/resource build before publishing.

## Managed runtime synchronization

At runtime, GSD synchronizes bundled resources into the managed agent directory, including:

```text
~/.gsd/agent/extensions/
```

`initResources()` can skip the full sync when the managed-resource manifest's package version and content fingerprint match the current bundled resources.

Consequences:

- editing only `src/resources` does not affect a normal release when complete `dist/resources` exists;
- editing `dist/resources` without updating the precomputed fingerprint can leave the existing managed extension copy unchanged;
- editing `~/.gsd/agent/extensions/subagent` directly is not durable because a later managed-resource refresh may replace bundled content.

## Previous viable options

Before the managed-fork decision, the spike left two possible distribution mechanisms:

1. exact-version prebuilt `dist/resources` overlay + regenerated fingerprint + controlled resync;
2. complete patched source build.

## Current consequence

The repository strategy has since changed. `penggin/gsd-pi-herdr` is now the full downstream GSD source distribution, so option 2 is the natural production model and the resource-overlay mechanism is no longer necessary as the primary architecture.

The finding still matters because it documents why:

- downstream releases must run the normal resource build/copy pipeline;
- testing source files alone is insufficient proof of packaged behavior;
- the internal Herdr integration/worker code must be included in the built/package resource layout where appropriate;
- post-build smoke tests should verify the actual packaged/runtime entrypoints.

## Source areas originally inspected

## Decision carried forward

Do not implement the Herdr integration as a `src/resources`-only patch against a published upstream package. Build this managed downstream fork through the normal GSD resource/package pipeline and validate the resulting runtime artifacts.
